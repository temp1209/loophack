# 要件定義

要件はこの1ファイルに集約する。変更した場合は上書きせず、末尾の
[変更履歴](#変更履歴)に理由付きで追記すること。

## 目的・コンセプト

- 究極的な目標はメンタルの安定。日常の行動を記録・可視化し「良い行動の継続」
  「習慣の安定化」につなげる
- 過去に習慣の継続へ何度も失敗しており、「何をすれば続けられるのか」自体を
  探る実験でもある
- コアコンセプトは「なるべく操作なしに記録する」。手入力ログではなく、行動に
  伴う事象（スマホのセンサー・スマート家電の状態変化等）をトリガーに自動記録する
- **成功の定義**: 「無意識化」と「可視化」のどちらが効くかを比較検証したい
  わけではない。この2つは対立しない。本音は「仕組みを作ること自体を楽しめる」
  性質を活かし、その仕組みづくりを通じて生活が豊かになった成功体験が欲しい、
  という点にある。分析・可視化機能は「AとBどちらが正解か」を決めるためではなく、
  作った仕組みと生活の質の変化を結びつけて実感するために存在する

## 対象行動

フェーズで区切らず、機能・修正単位で実装を進める（区切りが曖昧になりやすいため）。
現時点で見えている対象行動は次の2グループ：

- **スマホ単体で検知可能**（Wi-Fi接続変化、Bluetooth接続変化、Activity
  Recognition API、充電状態、Sleep API等）: 睡眠、帰宅・外出、仮眠開始など。
  実装難易度・依存が低いため先行して着手する
- **周辺デバイス連携が必要**: 入浴・洗濯（NFCタグ経由。SwitchBot製NTAG216・
  防水仕様、購入済み。浴室・洗濯機（半屋外設置）に貼る想定）、歯磨き等の
  完了チェック型の習慣、プランクなどAlexa/Home Assistant連携が絡むもの。
  Home Assistant自体は別マシン・別リポジトリで管理し、このリポジトリは
  Androidアプリ本体に集中する（元Minecraftサーバー機を転用予定、
  Core i3第7世代・メモリ16GB・SSD250GB程度）

## 対象外・制約

- ウェアラブル（バンド型）は身につけない。環境設置型センサー（スマートプラグ、
  温湿度センサー等）は問題ない
- kakeibo-app（既存の自作家計簿アプリ）は自動同期・クラウドバックアップが無く、
  手動JSONエクスポートのみが現状のデータ持ち出し手段
- kakeibo-appとの統合は「kakeibo-appを多機能化する」のではなく「loophackが
  "支出"という記録種別の一つとしてkakeibo-appのAI解析パイプライン設計を
  取り込む」方向で検討している（食事記録もあわせて）。詳細は下記
  「kakeibo-appとの統合方針」と [decisions.md](./decisions.md) を参照。
  現時点では方向性のみで、実装優先度・スキーマは未設計のため対象外

## 合意済みの設計方針

### 記録の土台（Event抽象）

行動種別ごとに専用テーブルを作るのではなく、共通のイベント抽象を核にする。

- `行動種別` / `開始時刻` / `終了時刻（nullなら瞬間イベント）` /
  `検知トリガー種別（Wi-Fi接続変化・Activity Recognition・Sleep API・充電状態等）` /
  `確度・信頼度` / `手動補正フラグ` / `メタデータ`
- 対象行動が増えてもEvent自体のスキーマは変えず拡張できることを狙う
  （マスタ管理 or 拡張しやすいenum設計は実装時に検討）

### アプリの構成（単一アプリ・機能単位モジュール分割）

kakeibo-appのような単機能アプリへの分割はしない。行動ごとの横断ダッシュボード
（生活の質の変化を実感するための企画の核）が作れなくなるため。代わりに、
アプリは1つのまま内部を機能単位（睡眠パッケージ、帰宅/外出パッケージ等）の
モジュールに分割し、パッケージ間は検知ロジックについて疎結合にする。Event
抽象とダッシュボードだけを共通の基盤として横断的に持たせる。検討の経緯は
[decisions.md](./decisions.md) を参照。

### 曖昧さの扱い

検知トリガーの解釈が一意に定まらない場合（例: Wi-Fi切断＝外出か電波不調か）は、
**自動記録＋信頼度スコア＋あとからの手動補正**で解決する。自動判定の精度だけで
完結させようとしない。

### 主観指標

気分・疲労度などの主観データも記録対象に含める。手法は、時間トリガー（特定の
タイミング）で気分・疲労度を尋ねる形式。行動記録と同じEvent抽象に乗せ、
時系列で突き合わせられるようにする。

### サーバー導入・同期を見据えた設計

Phase 1自体はサーバー無し（オンデバイス記録のみ）で進めるが、将来的に
Home Assistant用マシン（別リポジトリで管理）を、家計簿アプリの外部API呼び出し
（ローミング中の不達などで不安定さが表面化している）を肩代わりする窓口を
兼ねた個人用の共有バックエンドとして位置づける構想がある。loophackもPhase 2で
このサーバーとの同期・バックアップ先として使う可能性が高いため、Event抽象は
「後からサーバー同期を付け足せる」ことを前提に設計する（例: ローカル生成ID
での衝突回避、同期済み/未同期フラグ等）。実装時にサーバーの有無を前提とした
作り込みはせず、あくまで後付け可能な余地を残す程度に留める。

### kakeibo-appとの統合方針

食事記録（カロリー等）をkakeibo-appに統合する案（写真送信→レシートか食事か
をAIが判定→分岐）は却下し、逆方向を採用する: **kakeibo-appを多機能化せず、
loophack側に「支出」という記録種別の一つとして、kakeibo-appで確立したAI解析
パイプライン（撮影→AI解析→構造化データ→確認/修正→保存）の設計を移植する。**
kakeibo-appのコードベース自体は改変せず、単機能アプリとして残したまま参考
実装として設計を書き写す（将来的な退役は妨げない）。

- 「習慣」という共通の親エンティティ（日時・種別・記録内容・AI解析結果）で
  支出記録・食事記録・その他の行動記録をくくり直す。既存のEvent抽象
  （行動種別／開始時刻／終了時刻／検知トリガー種別／確度・信頼度／手動補正
  フラグ／メタデータ）を拡張し、「検知トリガー種別」の一つとして「写真＋AI
  解析」を追加する形を想定
- ユーザーが記録種別を明示的に選択してから撮影する（AIによる種別自動判定は
  行わない）。判定誤りのリスクとAPI往復増を避けるため
- 検討の経緯・却下した案は [decisions.md](./decisions.md) を参照

### 可視化（ダッシュボード）

「AとBどちらが正解か決める」ためではなく、仕組みづくりと生活の質の変化を
結びつけて実感するためのダッシュボードを目指す。構成案：

- カレンダーヒートマップ（日単位で行動の有無/量を色の濃淡表示）
- 時系列トレンドグラフ（睡眠時間・在宅時間などの推移、週/月切り替え）
- 分布・統計サマリ（曜日別傾向、平均値など）

## 未決事項

- 技術スタック: kakeibo-appとの共通化（Kotlin/Ktor+Compose Multiplatform）を
  前提にせず、実装要件（バックグラウンドセンサー監視の継続性、Sleep API/
  Activity Recognition APIの制約等）が固まってから選定する
- 行動種別の追加方式（マスタテーブル管理 vs enum拡張）の具体的な設計
- 記録が少ない初期段階でダッシュボードをどこまで作り込むか
- 主観指標を尋ねるタイミング（時間トリガーの具体的な設計。固定時刻か、
  行動イベントに紐付けた相対トリガーか）
- Home Assistant用マシンを共有バックエンドとして使う構想の具体化（API設計、
  loophackとの同期方式、家計簿アプリとの役割分担）
- 「習慣」共通スキーマ（Event抽象へのAI解析結果・確認/修正フローの取り込み方）
  の具体設計
- kakeibo-app統合の実装優先度（Phase1のセンサー系行動より先か後か）
- コアコンセプト「なるべく操作なしに記録する」と、写真撮影を伴うAI解析記録
  （能動的操作）との整合性・境界線をどう明示するか
